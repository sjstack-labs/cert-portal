# 보안 모델

이 문서는 포털이 무엇을 신뢰하고 무엇을 지켜야 하는지 정리합니다. 코드를 바꿀 때 아래
불변식 중 하나라도 깨진다면 그 변경은 설계 변경이므로 이 문서를 먼저 고쳐야 합니다.

## 신뢰 경계

| 구성 요소 | 신뢰 여부 | 근거 |
|---|---|---|
| Cloudflare Access | 신뢰 | 사용자 인증과 **권한 정책**을 모두 담당합니다. 포털은 Access를 통과한 사용자를 구분하지 않습니다. |
| `step-ca` | 신뢰 | 발급 정책(유효기간, 확장, 허용 이름)을 최종 결정합니다. |
| 포털 호스트와 `step` CLI | 신뢰 | provisioner 비밀번호 파일을 읽을 수 있습니다. |
| 브라우저와 요청 본문 | 불신 | 모든 입력은 서버에서 다시 검증합니다. |
| `X-Forwarded-For` | 기본 불신 | `TRUST_FORWARDED_FOR`를 켠 경우에만 감사 로그의 IP로 사용합니다. 인증 판단에는 쓰지 않습니다. |

Access 정책이 곧 이 포털의 권한 정책입니다. Access를 통과한 사람은 어떤 기기 이름으로든,
WPA3와 VPN 인증서를 모두 발급받을 수 있습니다. 발급 대상을 제한해야 한다면 Access
정책에서 사용자를 좁혀야 합니다.

## 불변식

1. **포털은 CA 개인키를 갖지 않습니다.** 포털은 리프 키와 CSR만 만들고, 서명은 항상
   `step-ca`에 요청합니다.
2. **WPA3와 VPN의 CA 설정을 섞지 않습니다.** WPA3 발급은 `STEP_CA_*`만, VPN 발급은
   `VPN_STEP_CA_*`만 사용합니다. provisioner, Root CA, CA URL 모두 해당합니다.
3. **모든 경로는 인증 미들웨어 뒤에 있습니다.** 정적 파일과 존재하지 않는 경로를 포함해
   인증되지 않은 요청은 `401`을 받으며, CA 명령을 실행하지 않습니다.
4. **개발 모드의 인증 우회는 loopback에 묶여 있습니다.** `APP_ENV=development`는 loopback
   주소에만 바인딩되고 loopback이 아닌 요청을 거부합니다. 예외는 컨테이너 개발용
   `CONTAINERIZED_DEVELOPMENT`뿐이며, 이때도 호스트에는 `127.0.0.1`로만 게시합니다.
5. **비밀값을 로그나 응답에 남기지 않습니다.** PKCS#12 비밀번호, 개인키, provisioner
   비밀번호는 기록하지 않습니다. 내부 오류의 상세 원인은 로그에만 남기고, 응답에는 고정
   문구와 요청 ID만 보냅니다.
6. **외부 명령에는 시간과 개수 제한이 있습니다.** `step` 실행은 `STEP_TIMEOUT_SECS` 안에
   끝나지 않으면 종료되고, 동시에 진행되는 발급 수는 `MAX_CONCURRENT_ISSUANCES`를 넘지
   않습니다.
7. **실제 인프라 정보를 저장소에 커밋하지 않습니다.** 도메인, IP, Access 팀 이름, 파일
   경로, 비밀번호 파일은 `.env.*`와 호스트 파일로만 관리합니다.

불변식 3, 4, 2, 5, 6은 `src/router_tests.rs`의 테스트로 확인합니다.

## 알려진 한계

- **인증서별 폐기 기능이 없습니다.** 분실한 기기의 인증서는 `step ca revoke`로 직접 폐기해야
  하며, Wi-Fi(RADIUS)와 VPN 서버가 폐기 목록을 확인하도록 별도로 설정해야 실제 접속이
  차단됩니다.
- **사용자별 권한 구분이 없습니다.** 위 신뢰 경계를 참고하세요.
- **발급 이력은 감사 로그에만 남습니다.**
